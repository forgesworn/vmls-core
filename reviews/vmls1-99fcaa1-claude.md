## New or remaining findings

**N-01 (Low): envelope decoders still diverge on truncated multi-byte heads at map and key positions.** Rust compares the map head and each key as a raw byte (`lib.rs:117-120`, `:129`, `:138`, `:176-182`), so a wide uint head that is cut short, for example `a3 18` or a lone `b8`, is `NonCanonical`. The reader decodes a CBOR head at those positions (`verify-vmls.mjs:801-802`, `:808`, `:812`) and fails inside `take` with `Malformed` (`:161-168`). Contract §3 says to "validate the map and profile" without stating that heads are compared literally, and the envelope vectors and hostile corpus contain no such input. Consequence: the same class of third-implementer code disagreement AI-02 described, on inputs no vector pins. Minimal resolution: state in §3 that the map head and keys are compared as the exact bytes `a3`, `01`, `02`, `03`, compare them literally in the reader, and add one vector such as `a3 18`.

**N-02 (Low): fork-evidence version and length precedence diverge.** Rust checks the 10-byte header length, then the version, then the exact total length (`evidence.rs:61-68`, `:83`), so a 300-byte payload with version `2` is `UnsupportedVersion`. The reader checks total length first (`verify-vmls.mjs:709-710`) and returns `Malformed`. §10 does not pin this order and no vector covers it. Minimal resolution: one sentence in §10 and reorder the reader to check header length, then version, then total length.

**N-03 (Informational): §6.1's "`d` before `scope`" wording is less precise than both implementations.** Both implementations run the duplicate check for `d`, then the duplicate check for `scope`, and only then compare both values (`binding.rs:268-272`, `verify-vmls.mjs:437-439`). A wrong `d` value combined with a duplicate `scope` tag is therefore `CredentialMalformed`, which a literal reading of §6.1 could lead a third implementer to report as `CredentialNotPersonScoped`. Minimal resolution: state that both duplicate checks precede the value comparison.

**N-04 (Informational): AUDIT §9 states "the Node reader matches Rust" without qualification (`AUDIT-INTEROP.md:453-455`).** Given N-01 and N-02, the supported claim is agreement on every published vector and on the precedence cases the contract documents.

I found no regression in accepted wire bytes. The Rust decoders are unchanged for byte input; the only Rust behavioural change is the strengthening of `ForkEvidence::verify` for directly constructed values, which cannot affect parse-derived values because `parse` already enforced the pair rule. The nine original envelope cases, the 41 original binding cases, and the seven original manifest cases are present with the new cases appended. The reader's credential and envelope reorderings change codes only on combined-failure inputs, and those are now pinned by vectors. I could not confirm the new Appendix A hashes or the new vector signatures myself; the supplied results are consistent with the expected codes, since a failing signature in the two new binding cases would have produced `CredentialSignatureInvalid` rather than the recorded codes.
